# Payload `migrate:create` без снапшота = мина под прод-БД

Наступили при M0 (2026-07-26). Касается **всех сайтов экосистемы на Payload 3.75 + PG** (Сабантуй, Казанская, ДК Малмыж, Калинино) — поэтому шлю.

## Что произошло

`pnpm migrate:create m0_news_portal` на репо, где уже есть боевая начальная миграция, выдал **не инкремент, а полную схему с нуля**: `CREATE TABLE` на все 22 таблицы (включая существующие `pages`, `posts`, `media`, `users`) и — самое опасное — `down()` с `DROP TABLE ... CASCADE` по **всем** таблицам проекта.

Выглядит это правдоподобно: файл валидный, `up()` синтаксически корректен. Применить такое на прод — в лучшем случае ошибка «relation already exists», в худшем (при откате/`down`) снос боевых данных.

## Причина

Drizzle диффит новую схему против **последнего `.json`-снапшота** рядом с миграциями. У нас начальная миграция была закоммичена парой `.ts` + `.sql` **без `.json`** — диффить не с чем, поэтому «текущее состояние БД» считается пустым и генерится всё.

## Что делать (рекомендация)

1. **Коммитить `.json`-снапшот вместе с миграцией.** Мы это исправили: `20260726_141845_m0_news_portal.json` в репо, следующий autogen будет диффить корректно.
2. **Проверить остальные сайты кластера** — если в их `migrations/` тоже только `.ts` + `.sql`, первый же новый `migrate:create` даст ту же полную схему. Дёшево проверяется: `ls web/src/migrations/*.json`.
3. **Всегда читать сгенерированную миграцию глазами** перед применением, особенно `down()`. Мы переписали `up()`/`down()` вручную в инкрементальные и проверили `psql -f` на чистой БД (initial → m0) — этот шаг обязателен, автогену на слово верить нельзя.

Если у кого-то из сайтов снапшот тоже утерян, а схема уже разъехалась — восстанавливаемо: сгенерировать снапшот против актуальной БД до написания новой миграции.
